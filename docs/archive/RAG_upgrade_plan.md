[learner cognitive state architecture](learner_cognitive_state_architecture.md) and the HOPE
learning-quality metrics (KI — knowledge integration, KT — knowledge transfer, CT — critical
thinking, persistence, cognitive load) defined in
[model_dataset_architecture_report.md](model_dataset_architecture_report.md) §5, making Wini a

No re-vision and no re-embedding of existing content; all new passes run from caches.

## 2. Research Findings on the Two Developer Points

### 2.1 Point 1 — Cropped figure/formula images linked into the RAG

**What the research says.** Multimodal RAG over educational PDFs works best when each figure
is extracted with its surrounding context and paired with a context-aware caption generated by a
multimodal LLM; the caption makes the image retrievable through a text-only pipeline while the
image itself is served to the learner ([MIND-RAG, ICCV 2025 workshop](https://openaccess.thecvf.com/content/ICCV2025W/MRR%202025/papers/Yu_MIND-RAG_Multimodal_Context-Aware_and_Intent-Aware_Retrieval-Augmented_Generation_for_Educational_Publications_ICCVW_2025_paper.pdf);
[Artifex/PyMuPDF multimodal guide](https://artifex.com/blog/building-a-multimodal-llm-application-with-pymupdf4llm)).
PyMuPDF (already in the pipeline as `fitz`) can extract raster images, **vector drawings**
(`page.cluster_drawings()`), and tables separately — important because NCERT Maths figures are
mostly vector graphics, not embedded bitmaps
([PyMuPDF RAG conversion notes](https://medium.com/@pymupdf/rag-llm-and-pdf-conversion-to-markdown-text-with-pymupdf-03af00259b5d)).

**Pros**

1. Directly serves the architecture's representation-centric learning (§9): a learner weak in
   the `graphical` representation can be *shown* the actual parabola from the book, not a verbal
   description of it — this is exactly the KI/representation-translation evidence HOPE measures.
2. Dual coding: pairing the image with text improves comprehension and recall vs. text alone.
3. Zero hallucination risk for visuals — the image is the textbook's own figure, keeping the
   NCERT-grounding guarantee (§6.7 "ground everything in curriculum material").
4. Cheap: page renders already exist at 2× zoom; cropping is local PyMuPDF geometry work, no
   API cost except optional caption refinement.
5. The `figure_map` in the curated seed and 181 vision-extracted figure nodes already carry
   `page` + `label` + concept links — we only need to add the pixel crop and `image_path`.

**Cons / risks and mitigations**

| Risk | Mitigation |
|---|---|
| Vector-graphic clustering can over/under-segment (axis labels split from the curve) | Pad cluster bboxes; merge overlapping clusters; fall back to a Gemini bounding-box call for pages where clustering finds nothing usable |
| Label→crop matching can be wrong ("Fig. 2.4" matched to the wrong crop) | Anchor each crop to the nearest "Fig. X.Y" caption text span (PyMuPDF gives caption text coordinates); manual spot-check sample per chapter |
| Long formulas are text, not drawings — cropping them from the render needs bbox detection | Crop only *display* equations that vision already extracted as important (911 formula nodes); use the text-span bbox of the formula line(s), which PyMuPDF provides reliably |
| Storage growth | Crops are small PNGs (~10–50 KB); ~1,200 assets ≈ 30–60 MB. Keep full-page renders as-is |
| UI must be able to display images | Store `image_path` relative to the store root; the response layer decides whether to attach |

**Verdict: adopt.** Highest pedagogy-per-rupee item in the plan; mostly local computation.

### 2.2 Point 2 — Class-9 prerequisite bridges ("bridge-gap" recall)

**What the research says.** Activating accurate prior knowledge before new instruction is one of
the most consistently supported effects in learning science: it anchors new content to existing
schemas and measurably improves retention, organization, and transfer
([Hattan, Alexander & Lupo, *Review of Educational Research* 2024](https://journals.sagepub.com/doi/10.3102/00346543221148478);
[MIT Teaching+Learning Lab](https://tll.mit.edu/teaching-resources/how-to-teach/help-students-retain-organize-and-integrate-knowledge/);
[Virginia Tech CETL](https://teaching.vt.edu/teachingresources/adjustinginstruction/priorknowledge.html)).
Advance organizers help novices most — exactly the Class-10 student opening a new chapter
([CAST UDL guidelines](https://udlguidelines.cast.org/representation/building-knowledge/prior-knowledge/)).
A 2025 *Instructional Science* study found the *coverage* of relevant prior knowledge during
activation matters — partial activation gives partial benefit
([Springer](https://link.springer.com/article/10.1007/s11251-025-09727-6)) — so bridges must
systematically cover each chapter's stated Class-9 dependencies, not just one. NCERT chapters are
literally written this way: nearly every chapter's §x.1 Introduction recalls Class IX material
(51 store chunks already reference it).

**Pros**

1. Implements architecture Rule 6 ("sequence by prerequisites") *across grades*, which the store
   currently cannot do — today's prerequisite chains stop at the Class-10 book boundary (the 29
   dangling `unknown` nodes are partly this).
2. Gives the Pedagogical Decision Engine a real "redirect to prerequisite" action target (§6.6):
   when mastery of a bridge concept is unknown/low, serve the recap + one diagnostic question
   before the new concept.
3. The textbook's own introduction sections provide NCERT-grounded bridge text — minimal
   hallucination risk for the recap core.
4. Directly improves KT scoring: a bridge is by definition a near-transfer event ("use Class-9
   similarity idea in Class-10 triangles"), giving HOPE labeled transfer moments at chapter entry.
5. Cold-start fix for the Learner State Model: bridge diagnostic questions are the cheapest way
   to initialize mastery estimates for a brand-new learner.

**Cons / risks and mitigations**

| Risk | Mitigation |
|---|---|
| Class-9 textbook is not in the corpus — deep recaps could hallucinate beyond what Class-10 intros state | Two-tier design: tier 1 = verbatim NCERT intro chunks (grounded); tier 2 = short LLM-written `bridge_recap` (3–5 sentences) generated *only from* those intro chunks + concept summary, flagged `source: "generated"` |
| Inaccurate prior knowledge can interfere with new learning (well-documented caveat) | Every bridge carries one `diagnostic_question` + expected answer so the tutor *checks* the recall instead of assuming it |
| Grade-9 concept granularity is arbitrary (no Class-9 seed) | Keep bridges coarse: one `grade9_concept` node per named dependency in the intro text (e.g. "Heron's formula", "linear equations in two variables — Class IX"), ~3–6 per chapter |
| Over-bridging slows advanced learners | Pedagogy policy gates bridges on learner state: skip when bridge mastery ≥ threshold or learner ZPD band is high |
| Scope creep toward ingesting the full Class-9 book | Out of scope for this plan; the `grade9_concept` nodes are designed so a future Class-9 ingest can attach to them without schema change |

**Verdict: adopt.** Strong evidence base; the data source (intro sections) is already in the store.

## 3. End-to-End Implementation Plan

Phases are ordered by dependency. Each phase lists steps, files, outputs, and verification.
LLM cost estimate for the whole plan: ~700 cached calls (no re-vision, no re-embedding of
existing chunks; only new bridge/caption texts get embedded).

### Phase 0 — Baseline scorecard (½ day)

> Make the gaps measurable before changing anything, so every later phase proves its delta.

1. Extend [verify_store.py](verify_store.py) into a **HOPE-readiness scorecard** that prints
   per-metric coverage:
   - % concepts with `difficulty`, `transfer_links` (≥2 near + ≥1 far), `integration_links`
     (≥1), `ct_probes` (≥2), `applications` (≥1), `vocabulary`;
   - % misconceptions with `why_wrong` + `correct_idea` + `diagnostic_question`;
   - % figure/formula/table nodes with `image_path`;
   - count of dangling prerequisite nodes (target 0);
   - % chapters with ≥1 grade-9 bridge; % bridges with diagnostic question;
   - % chunks concept-linked and difficulty-tagged (already 100%, guard against regression).
2. Run it; commit the baseline numbers at the top of the report output.
3. Add `--fail-under <pct>` so later phases can gate rebuilds.

**Output:** `verify_store.py` scorecard mode, baseline report.
**Verify:** baseline matches the gap table in §1.

### Phase 1 — Concept-card enrichment (`enrich_concepts.py`, new) (1–2 days)

> Closes G1, G2, G3 (concept side), G4, G5, G6.

1. New script `enrich_concepts.py`, same cache pattern as `pedagogy_enrich.py`
   (`concept_enrich_cache.jsonl`, resumable, one JSON-mode call per concept).
2. For each of the 108 concepts, build a grounded prompt from: the concept card, its own chunks
   (filtered by `concept_ids`), its graph neighbors (formulas/examples/misconceptions), and the
   full list of 108 valid concept IDs. Generate:
   - `difficulty` (1–9) — anchored to the median difficulty of the concept's own
     chunks/exercises (provided in-prompt) so it stays on the existing ZPD scale;
   - `transfer_links` — ≥2 near (must be IDs from the 108; cross-chapter allowed, e.g.
     `jemh102__quadratic_coefficients → jemh104__quadratic_equation_definition`) + ≥1 far
     (real-world/Science domain with a `note` explaining the bridge). Re-inject the curated
     Polynomials links from [chapter_seed_polynomials.json](chapter_seed_polynomials.json) verbatim;
   - `integration_links` (KI) — concepts this one combines with, each tagged with the
     representation pair being translated (e.g. `symbolic↔graphical`);
   - `ct_probes` (CT) — 2–3 edge-case/"why" questions + 1 counterexample sketch, each with an
     expected-insight rubric line;
   - `applications` — promote the existing 227 application graph nodes onto their source
     concept cards, letting the LLM dedupe/normalize;
   - `vocabulary` — chapter key terms (supersedes the `aliases` proxy; keep `aliases` too);
   - `metacognitive_prompts` (A1.4) — 2 post-solve self-explanation prompts per concept
     ("explain the steps you took to a Class 9 student", "which step was trickiest and why?"),
     tagged `when: "after_success" | "after_struggle"` so the pedagogy engine retrieves them at
     the right moment; feeds HOPE persistence/load signals.
3. **Validation layer (hard):** reject any `transfer_links`/`integration_links` target not in
   the 108-ID list; one retry with the error fed back, then drop and log.
4. Misconception enrichment in the same script (batched, ~30 per call over the 276 nodes):
   add `why_wrong`, `correct_idea`, `diagnostic_question` to every misconception node.
5. **Problem-schema extraction (A1.1 + A1.3):** per concept, cluster its worked examples and
   exercises (286 + 647 nodes, grouped via existing `has_example`/`has_exercise` edges) into
   **problem types**; emit `problem_schema` nodes
   (`schema::<concept>::<slug>`, fields: `name` e.g. "upstream/downstream speed word problem",
   `method_steps` — the ordered algorithmic steps, `instance_ids` — the example/exercise nodes
   instantiating it, `isomorphic_variables` — which surface variables can be swapped
   (names/numbers/contexts) without changing mathematical structure or difficulty, plus
   `trap_steps` — the steps where the linked misconceptions typically bite). Edges:
   `concept -[has_schema]-> problem_schema -[instantiated_by]-> example/exercise`.
   This is what lets retrieval serve an *analogous worked example* when a student is stuck on a
   specific problem type, instead of re-explaining the concept. ~108 batched calls.
6. **Hint-chain generation (A1.2):** for every exercise node and every diagnostic question,
   generate `hint_chain`: exactly 3 ordered hints — (1) conceptual nudge, (2) formula/method
   recall, (3) partial first step — with the hard rule that no hint states the final answer.
   Grounded in the matching `problem_schema.method_steps`. Batched ~25/call over 647 exercises
   + 276 diagnostics ≈ 40 calls. This is the data the architecture's "faded hint" action (§6.6)
   retrieves, and it caps what the response layer is allowed to reveal per hint request.
7. Write enriched cards to `concepts.json` (additive — no existing field is removed or renamed,
   so `query.py`/`rag_core.py` keep working mid-migration).

**Output:** enriched `concepts.json`, new `problem_schema` nodes in `graph.json`,
`hint_chain` on exercise/diagnostic nodes, `concept_enrich_cache.jsonl`.
**Verify:** scorecard — 100% difficulty, ≥95% transfer/integration/probe coverage, 100%
misconception enrichment, ≥90% concepts with ≥1 problem schema, ≥95% exercises with a
3-step hint chain (no hint containing the answer — automated regex + sample audit);
spot-check 10 random concepts by hand.

### Phase 2 — Visual asset extraction (`crop_figures.py`, new) (2–3 days)

> Closes G8 (developer point 1).

1. New script `crop_figures.py`. For each PDF page (PyMuPDF, local, no API):
   - **Vector figures:** `page.cluster_drawings()` → candidate bboxes; pad by ~8 px; merge
     overlaps; drop tiny clusters (< ~1% page area, usually rules/underline strokes).
   - **Raster images:** `page.get_images()` → bbox via `page.get_image_rects()`.
   - **Caption anchoring:** locate "Fig. X.Y" / "Table X.Y" text spans
     (`page.search_for`); assign each crop to its nearest caption *below or beside* it; the
     caption string becomes the crop's `label` — this is the join key to the existing 181
     figure / 64 table nodes.
   - **Display formulas:** for the 911 formula nodes, find the formula text span on its page
     (`page.search_for` on the formula string, fuzzy-normalized); crop the line block with
     padding. Skip silently when not found (inline formulas don't need crops).
   - Render crops from the existing 2× pixmap; save to
     `rag_store/figure_crops/<doc_id>/<node_id>.png`.
2. **Fallback for unmatched figure nodes:** one Gemini call per *page* that has figure nodes
   but no caption-matched crop, asking for normalized bounding boxes of each labeled figure
   (Gemini returns `[y0,x0,y1,x1]` in 0–1000 space). Estimated < 40 pages.
3. Graph update (in `crop_figures.py`, patching `graph.json`): add `image_path`, `bbox`,
   `crop_source` (`cluster|caption|gemini|none`) to figure/table/formula nodes.
4. **Caption + representation-semantics enrichment (extended per A2.5):** for every cropped
   figure/table, one batched vision call on the *crop* (not the full page) producing:
   - `alt_text` — pedagogically rich description (what it shows + what the learner should notice);
   - `supports_representation` — which of the 8 store representation types this asset teaches
     (e.g. `graphical`), wired as a `represented_by`-parallel edge so KI retrieval can ask
     "give me the *graphical* form of this concept";
   - `disambiguates_misconceptions` — misconception IDs this visual directly refutes (e.g.
     Fig. 2.5 refutes `quadratic_always_has_two_real_zeroes`), validated against the 276 nodes;
   - `good_for_questions` — 1–2 interpretive question stems answerable *from this visual*
     ("how many zeroes does this parabola show?");
   - `addresses_gap` — the learner-state condition this asset serves
     (`representation_missing: graphical`, `misconception_active: <id>`).
   A crop without these fields is dead weight for KI — the semantics are what let the
   retrieval layer pick the *right* visual for the *current* learner gap.
   Embed `label + alt_text` as new retrievable mini-chunks (`kind: "figure_caption"`, linked by
   `figure_id`) appended to `chunks.jsonl` + FAISS, so "show me the graph of a quadratic with
   no real zeroes" retrieves Fig. 2.5 directly.
5. Spot-check: render a contact sheet (HTML) of all crops per chapter for 5-minute human review.

**Output:** `rag_store/figure_crops/**`, patched `graph.json`, new caption chunks, contact sheet.
**Verify:** scorecard — ≥90% of figure/table nodes and ≥60% of formula nodes have `image_path`;
contact-sheet review finds < 5% bad crops.

### Phase 3 — Class-9 bridge layer (`build_bridges.py`, new) (1–2 days)

> Closes G9 (developer point 2) and most of G7.

1. **Detect bridge material:** scan `chunks.jsonl` for intro-section chunks (page ≤ 4 of each
   doc, or text matching `Class IX|you have studied|recall that|in the previous class`) — the
   51 known chunks plus pattern hits. Tag them `pedagogical_role: "bridge_recall"` (new role,
   added to `pedagogy_enrich.py`'s role enum for future rebuilds).
2. **Extract grade-9 dependencies:** one LLM call per chapter (16 calls) over its intro chunks +
   chapter summary: list the named Class-9 concepts the intro leans on (3–6 each), with for
   each: `name`, `grade9_topic` (NCERT Class-9 chapter name), `bridge_recap` (3–5 sentence
   recall explanation grounded ONLY in the supplied intro text), `diagnostic_question` +
   `expected_answer`, and the Class-10 `target_concept_ids` (validated against the 108).
3. **Graph integration:** create `grade9_concept` nodes
   (`grade9::<slug>`, fields: name, grade: 9, topic, recap, diagnostic, `source: "generated"`)
   with edges `grade9_concept -[bridges_to]-> class10_concept` and
   `bridge_chunk -[evidence_for]-> grade9_concept`.
4. **Dangling-prereq resolution (G7):** alias-match the 29 `unknown` prerequisite nodes against
   (a) the 108 concept IDs, (b) the new grade-9 nodes. Re-point matches; convert genuine
   externals to typed `external_concept` nodes with a grade tag; target 0 `unknown` nodes.
5. **Learner-state hook:** add bridge concepts to [learner_state.py](learner_state.py) mastery
   map (cold-start 0.30 like any unseen concept).
6. Embed each `bridge_recap` as a retrievable chunk (`kind: "bridge_recap"`).
7. **Explicit bridge policy contract (A2.4)** — bridges are runtime-gated learner-state objects,
   not just graph insertions. The contract, implemented in `learner_state.py` + `query.py`:
   - **Activate** a bridge only when the resolved Class-10 concept has a `bridges_to`
     predecessor whose mastery is unknown (cold-start) or `< 0.6`, AND the bridge was not
     already served this session;
   - **Skip** when bridge mastery `≥ 0.6` or the learner's ZPD band center `≥ 7` (advanced
     learners are not slowed by recaps);
   - **Feedback loop:** the bridge diagnostic is never display-only. Its outcome writes back:
     correct → bridge-concept mastery `+0.25` (capped) and proceed; wrong/partial → mastery
     `-0.10`, set any revealed misconception to `active`, and the pedagogy engine serves the
     recap *before* the new concept. New `learner_state.py` API:
     `apply_bridge_result(bridge_id, outcome)` — this is what turns the bridge from a "recap
     widget" into part of the cognitive model, and doubles as the cold-start mastery probe.

**Output:** patched `graph.json`/`chunks.jsonl`/FAISS, `bridge_cache.jsonl`, role enum update,
`apply_bridge_result` in `learner_state.py`.
**Verify:** scorecard — 16/16 chapters have ≥1 bridge, 100% of bridges have diagnostic
questions, 0 dangling prereq nodes; read all ~60 recaps once (small enough for full review).

### Phase 5 — Retrieval upgrades in [query.py](query.py) (1–2 days)

> Make every new asset reachable by the Pedagogical Decision Engine (§6.6/§6.7), and make the
> ranking depend on the *learner snapshot*, not only the query (A2.1).

1. **Learner-state-aware ranking contract (A2.1).** Replace the current 3-term re-rank
   (`0.70*relevance + 0.20*difficulty_fit + 0.10*role_match`) with an explicit scored policy
   over the full learner snapshot. Per candidate evidence item:

   ```text
   score = w1*semantic_relevance            (query ↔ chunk, as today)
         + w2*difficulty_fit                (chunk difficulty vs ZPD band, as today)
         + w3*role_match                    (pedagogical_role vs decided action)
         + w4*representation_gap_fit        (asset's representation ∈ learner representations_missing)
         + w5*misconception_priority        (asset linked to a misconception with status active/recurring)
         + w6*hint_dependency_penalty       (suppress full worked examples when hint_dependency > 0.5;
                                             prefer hint_chain step k+1 instead)
         + w7*hope_history_boost            (recent low KI → boost integration evidence;
                                             recent low KT → boost transfer evidence; etc.)
   ```

   Initial weights hand-set, logged per turn so they can later be tuned from the append-only
   learning log (architecture §12.2). The snapshot consumed: current concept, mastery,
   misconception map + statuses, representations_known/missing, ZPD band, hint dependency,
   rolling KI/KT/CT scores, items already served this session (no-repeat).
2. **KT need** → follow `transfers_to`: near first; far only when source-concept mastery is
   high (matches §6.6 "near-transfer first, far-transfer later"). When stuck on a specific
   problem, retrieve the matching `problem_schema` and serve an *analogous* worked example from
   `instance_ids` (A1.1) rather than re-explaining the concept.
3. **KI need** → use `integrates_with` + the learner's `representations_missing` to pick the
   representation-translation evidence; attach the figure crop whose `supports_representation`
   matches the missing representation and whose `addresses_gap` matches the learner condition.
4. **CT need** → retrieve `ct_probe` / counterexample nodes at the learner's ZPD band; after a
   successful solve, retrieve a `metacognitive_prompt` (`when: after_success`).
5. **Misconception mechanics (A2.6) — probe → diagnose → correct state machine.**
   Misconception nodes follow architecture §10 statuses (`active / weakening / resolved /
   recurring`) and retrieval order is enforced, never correction-first:
   - status `suspected/active` → retrieve `diagnostic_question` (+ its `hint_chain`) FIRST;
   - diagnostic wrong → retrieve `why_wrong` + `correct_idea` + the disambiguating figure crop
     (`disambiguates_misconceptions`); status stays `active`, confidence up;
   - diagnostic right → status `active → weakening`; after 2 consecutive successes spaced
     across sessions → `weakening → resolved`; a later failure → `resolved → recurring`
     (priority-boosted by `w5` above).
   - **Write-back (A2.4):** every probe outcome updates the learner's misconception confidence
     and concept mastery via a new `learner_state.py` API
     `apply_probe_result(misconception_id, outcome)` — same pattern as `apply_bridge_result`.
6. **Bridge gate** → apply the Phase 3 step 7 policy contract: activate/skip by prerequisite
   mastery and ZPD; prepend `bridge_recap` + diagnostic to the evidence pack when activated.
7. **Evidence provenance pack (A2.2).** `query.py` returns (and the turn log persists) a
   structured evidence manifest with every response:

   ```json
   {
     "evidence": [
       {"id": "jemh102::page_005::chunk_001", "type": "chunk", "why": "explains case (ii) equal roots"},
       {"id": "fig::jemh102::fig_2_4", "type": "figure", "image_path": "figure_crops/jemh102/fig_2_4.png",
        "why": "graphical representation gap"},
       {"id": "misconception::quadratic_always_has_two_real_zeroes", "type": "misconception",
        "why": "status=active, diagnostic served"}
     ],
     "bridge_ids": [], "schema_ids": [], "ranking_trace": {"w4_repr_gap": 0.31}
   }
   ```

   The response layer must compose only from manifest items — this is what keeps every
   generated sentence traceable to an exact chunk/figure/bridge/misconception node
   (architecture §12.2 "retrieval evidence"), and it makes grounding *auditable* (see §4b).

   > **Documented exception (Part 11, 2026-07-01).** Two reply paths are NOT store-grounded and
   > are not required to be: (a) the **perception** call, which reads an utterance and emits
   > structured JSON (intent/signals/concept) — schema-grounded, writes nothing; and (b) the
   > **non-LEARNING** replies (SOCIAL / META_CAPABILITY / OFF_DOMAIN_ACADEMIC / EMOTIONAL /
   > SESSION_CONTROL / SAFETY / NONSENSE), which are **persona-grounded** (`persona.json`;
   > SAFETY/NONSENSE fully scripted) rather than manifest-grounded. They are only reachable when
   > the front door routes away from `LEARNING`; every `LEARNING` answer stays manifest-only and
   > auditable. See `PART11_GEMINI_PERCEPTION_LAYER.md` §4.3.
8. **Bundle cohesion check (A1.5, cost-gated).** Before generation, validate that the retrieved
   bundle is coherent: (a) always-on structural checks — every evidence item must be within 2
   graph hops of the resolved concept, difficulty spread ≤ 3 bands, no `correct_idea` present
   without its misconception being in the bundle; (b) only when the bundle mixes ≥3 source
   types (e.g. bridge + concept + misconception), one cheap LLM self-check ("do these
   contradict each other? YES/NO + which") that can drop the offending item. No per-turn judge
   call on simple bundles — latency and cost stay flat for the common case.
9. Add `--need transfer|integrate|challenge|bridge|schema|reflect` modes and a
   `--snapshot <learner_state.json>` arg for manual testing.

**Output:** upgraded `query.py`, `apply_probe_result` in `learner_state.py`, evidence manifest
in the turn log.
**Verify:** scripted smoke tests — low-mastery learner on similar triangles gets the Class-9
similarity bridge first and the diagnostic outcome moves stored mastery; learner with
`hint_dependency 0.7` asking for help gets hint 2 of the chain, not the worked example;
graphical-gap learner gets Fig. 2.4's crop; misconception probe wrong → `why_wrong` appears
*after* the diagnostic, never before; every test response carries a non-empty evidence
manifest whose IDs all exist in the store.

### Phase 6 — HOPE dataset bootstrap (`build_hope_bank.py`, new) (1 day)

> Closes G10 = report §5.6 step 1: "start with curated transfer, representation, and
> critical-thinking prompts."

1. Generate `hope_prompt_bank.jsonl` straight from the enriched store — for each concept:
   - KI prompts from `integration_links` (representation-translation tasks, optionally
     referencing a figure crop);
   - KT prompts from `transfer_links` (near and far, with the `note` as rubric anchor);
   - CT prompts from `ct_probes` (edge cases, counterexamples);
   - bridge prompts from grade-9 diagnostics (persistence/cold-start signals).
2. Each row: `prompt`, `concept_id`, `signal` (KI/KT/CT), `difficulty`, `bloom_level`,
   `rubric_anchor`, `figure_id?` — the exact shape report §5.4 labels (0–3 ordinal) attach to.
3. Target ≥ 1,000 curated prompts (108 concepts × ~9), the seed corpus toward the 5,000+
   labeled examples per HOPE signal the report requires.
4. **Teacher-calibrated gold set BEFORE scaling (A2.3).** Generation alone risks prompts that
   are syntactically fine but pedagogically shallow. Before the bank is used for any HOPE
   training or scoring:
   - sample ~300 prompts stratified by signal × difficulty; for each, generate 4 synthetic
     student answers at weak / memorized / partial / strong levels (report §5.6 step 2);
   - have ≥2 teachers (or 1 teacher + 1 independent LLM judge with a written rubric) label each
     answer 0–3 per signal; compute inter-rater agreement; **gate: Cohen's κ ≥ 0.6 per signal**
     before any scaling — disagreements resolved by expert, rubric amended;
   - the rubric must explicitly force the three discriminations the architecture cares about:
     *memorized answer vs. representation translation* (KI), *surface analogy vs. structural
     transfer* (KT), *curiosity vs. genuine critical evaluation* (CT). Prompts on which strong
     and memorized answers get the same score are rewritten or dropped.
5. Output `hope_gold_set.jsonl` (~1,200 labeled answers) — the calibration anchor for the
   future HOPE detector and the LLM-judge prompt.
6. Only after the κ gate passes, scale the bank generation to the remaining concepts/variants.

**Output:** `hope_prompt_bank.jsonl`, `hope_gold_set.jsonl`, rubric doc, `build_hope_bank.py`.
**Verify:** counts per signal ≥ 300; κ ≥ 0.6 per signal on the gold set; 30-prompt random
sample human-reviewed; memorized-vs-strong answers separated by ≥1 ordinal level on ≥85% of
gold items.

## 6. Cross-Cutting Risks

1. **LLM-generated pedagogy is not hand-vetted** (non-Polynomials concepts already have this
   caveat). Mitigation: hard ID validation, grounding every generation in the concept's own
   chunks, human spot-checks at every phase gate, `source: "generated"` flags on all synthetic
   text so the response layer can attribute confidence.
2. **Schema drift** breaking `query.py` mid-migration. Mitigation: all changes additive;
   `store_schema_version` in `meta.json`; scorecard runs after every phase.
3. **Windows/encoding traps** (NCERT private-use glyphs crashed cp1252 before). All new
   scripts write UTF-8 explicitly and set `sys.stdout.reconfigure(encoding="utf-8")`.
4. **Vertex env**: all LLM phases need `GOOGLE_GENAI_USE_VERTEXAI=True`,
   `GOOGLE_CLOUD_PROJECT`, `GOOGLE_CLOUD_LOCATION=global` (see `cloud_env.bat`).
