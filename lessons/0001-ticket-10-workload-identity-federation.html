Ticket 10: Workload Identity Federation for Billed CI

How we securely authenticate to Vertex AI and protect cloud spend without static API keys

1. The Problem: The Perils of Static Service Account Keys

In automated test pipelines, models often need to run against live cloud APIs (like Google Cloud Vertex AI) to compute evaluation metrics such as safety recall and PII precision.

The legacy approach was to generate a long-lived service account JSON key file and paste it into GitHub Repository Secrets. This causes three critical vulnerabilities:

  • Secret Leaks: A static key in CI can easily be dumped in logs, leaked through malicious PRs, or compromised if developer laptops are exposed.
  • Runaway Billing Spend: Any commit or automated PR run can trigger thousands of LLM calls, draining quotas and budgets.
  • Fork Exploits: Workflows triggered on external forks could potentially inherit repository-level secrets.

2. The Architecture: Workload Identity Federation (WIF)

Ticket 10 solves this by using Workload Identity Federation. Rather than storing a static secret, GitHub Actions negotiates an ephemeral OpenID Connect (OIDC) token on the fly.

The OIDC Authentication Handshake

  1. GitHub Actions runner requests an OIDC token from GitHub's OIDC provider.
  2. GitHub issues a cryptographically signed JWT containing claims (e.g., repository name, environment).
  3. The google-github-actions/auth@v2 action presents this JWT to GCP Workload Identity Pool.
  4. GCP verifies the signature and checks the attribute condition: 
    assertion.repository == 'org/repo' && assertion.environment == 'billed-eval'
  5. If valid, GCP allows the federated principal to impersonate the dedicated service account (wini-billed-ci) and returns a short-lived OAuth2 token for Vertex AI.

3. The Implementation in Our Codebase

Ticket 10 was implemented across two key files in the repository:

1. CI Workflow: .github/workflows/ci.yml

Added two new jobs: billed-safety and billed-personal-data. Key design properties:

  • needs: [offline] — The billed jobs only run after the free, offline test suite passes completely.
  • environment: billed-eval — Placed behind a GitHub Environment that requires human reviewer approval before execution.
  • permissions: id-token: write — Grants the runner permission to fetch the OIDC JWT token.
  • Guard Step — Checks that WIF_PROVIDER and WIF_SERVICE_ACCOUNT exist. If missing, outputs a clear error annotation instead of failing cryptically.
  • Stub Gate — Exits with code 1 until Tickets 12 & 13 land their real evaluation commands, preventing false green passes in CI.
2. Operator Setup Guide: .github/BILLED_EVAL_SETUP.md

Documents the exact gcloud commands required to:

  • Create the Workload Identity Pool (github-actions-pool) and OIDC Provider (github-oidc).
  • Create the dedicated service account (wini-billed-ci) with roles/aiplatform.user.
  • Bind roles/iam.workloadIdentityUser strictly to the billed-eval environment principal set.
  • Configure the GitHub Environment secrets.

4. How Ticket 10 Fits Into the Bigger Roadmap

Ticket 10 was an independent prerequisite that unblocks the downstream vertical slices:

  • Ticket 12 (Child Safety Stage 2): Ships eval/safety_eval.py --collect which evaluates safety recall against live Vertex AI Gemini models in asia-south1.
  • Ticket 13 (Personal Data Stage 3): Ships eval/personal_data_eval.py --collect which measures PII extraction and redaction precision across ≥500 test rows.

To allow any PR commit to automatically test the model without requiring manual reviewer interaction
To configure the cloud runner to run offline tests in parallel with live Vertex AI billing evaluations
To ensure tokens are only granted after a reviewer explicitly approves the billed evaluation run
To allow third-party contributors on unapproved repository forks to consume cloud credits freely

Because the GCP service account credentials expired immediately after being created by the developer
To prevent CI from falsely reporting green passes before Tickets 12 and 13 deliver the real eval steps
Because GitHub Actions workflows cannot parse Google Cloud Workload Identity Federation JSON responses
To signal that the free offline unit test runner needs to be recompiled under the new Python runtime
